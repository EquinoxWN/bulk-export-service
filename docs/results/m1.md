# M1 results

Measured on 2026-11-17 on Windows 11, Intel Core i7-13700H, 13.7 GB RAM (other builds running in
parallel), Go 1.26.11. No PostgreSQL runs on this machine (no Docker): the PostgreSQL parts are
covered by tests that run in CI against a `postgres:17.11` service container and **have not run
yet** (no push so far). The race detector needs cgo, which this machine lacks; CI runs `-race`.

## Measure: the in-process run

```bash
go run ./cmd/bulk-export-service demo -rows 20000      # same as make bench
```

```
config: accounts=20 orders/account=20000 page=1000 workers=4 page-read failures=every 7
create: 20 jobs queued (202) and 20 retries replayed the same id (200) in 8ms, before any worker started
exports: 20 succeeded, 0 failed, 400000 rows in 420 pages, 390 status polls, 341ms, 69 page reads retried
rows examined (in-memory model, not a database measurement): keyset 400000, OFFSET for the same pages 4600000 (11.5x)
verify: files=20 rows_checked=400000 row_mismatches=0 count_mismatches=0 sha_mismatches=0 failed_jobs=0
```

Method: the "replica" is an in-memory table (`source.Memory`, binary search to the cursor, like an
index seek) holding 20 accounts x 20,000 synthetic orders where every three orders share a
`created_at`. All 40 create calls (20 new, 20 retries) go over real HTTP on 127.0.0.1 before any
worker starts. Four workers then export, with every 7th page read failing once on purpose. The demo
polls the status endpoint, downloads each file, checks its SHA-256 and byte count against the job,
and compares every row with a separate one-row-per-page walk of the source. "Rows examined" counts
rows the source returned for keyset pages, and rows walked past plus returned for OFFSET pages over
the same table: a model of database work, not a database measurement. The time (341 ms) is
wall-clock on a loaded laptop and only shows the run is quick; it is not a benchmark.

The API run (in-memory `serve`, 3 accounts x 50,000 orders, curl) is in `docs/proof/api.jpg`: 202
`queued` with 0 rows, 200 `Idempotent-Replayed: true` for the retry, 400 for `parquet`, then
`succeeded` with 50,000 rows in 51 pages and a 3,066,782-byte file whose `sha256sum` matches the
stored hash. The first text cell starting with `-` shows the formula guard (`'-2 discount`).

## Analyze

- **OFFSET cost grows with page position.** For an export of `p` full pages OFFSET examines
  `n(1 + 2 + ... + p) + n p` rows (the last, empty page still walks past everything); keyset examines
  the `n p` rows it returns. With 20 pages per account that is 11.5x. The model also shows the
  correctness problem: `TestKeysetIsStableUnderInsertsWhereOffsetIsNot` inserts one early row between
  two pages and OFFSET returns a row twice (9 distinct rows out of 10), keyset does not.
- **Defect found in review and fixed:** worker ids were first `<host>-wN`, so two processes on one
  host would share ids and pass each other's ownership fence in the PostgreSQL store. Ids now include
  8 random hex characters per process.

## Improve and Control

- Keyset instead of OFFSET, a separate read-only reader pool, idempotent job creation and fenced job
  updates are the improvements; ADRs 0002 and 0003 record the trade-offs.
- CI gates (not run yet): `make ci` (gofmt, `go vet`, `go test -race`), `make audit` (govulncheck),
  the demo with a `::notice` of its `verify:` line, and `make test-pg` against PostgreSQL 17.11,
  which fails if any test skips.
- Mutation check: 15 of 15 hand mutations killed ([`docs/quality/2026-11-01.md`](../quality/2026-11-01.md)).
